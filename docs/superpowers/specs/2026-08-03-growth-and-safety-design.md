# 推广前安全加固 + 微信分享预览 + 打车对比设计稿

日期：2026-08-03

## 目标

这次设计围绕推广前最值得补的三件事展开：

1. 给公开统计接口和后台入口补上更稳的保护，降低被刷和被探测的风险。
2. 强化站点在微信等社交场景里的链接预览，同时让结果分享更有“这是一次真实测算结果”的感觉。
3. 增加一个轻量但有判断价值的“打车费用对比”，让用户能把“养车值不值”与“打车够不够用”放在同一页里快速比较。

这三件事必须同时满足一个约束：不能把当前页面做重、做乱，视觉主次仍然以“车辆成本结果”本身为核心。

## 范围

### 本次包含

- `/api/visit` 与 `/api/event` 的 rate limit 方案
- `/admin.html` 与 `/api/stats` 的双层保护方案
- 首页站点级社交分享预览优化
- 现有“文字分享 / 图片分享”链路中的轻量结果感增强
- 打车对比结论卡
- 打车对比参数组

### 本次不包含

- 动态服务端 OG 图
- 每个分享链接都生成单独的微信动态图文卡片
- 完整的用户账户体系或后台多角色权限
- 第二套独立的“打车计算器”页面
- 复杂城市级打车计价模板

## 一、推广前安全加固

### 1.1 风险判断

当前项目最现实的风险不是用户隐私泄露，而是：

- 访问量与事件埋点被脚本刷高，导致推广数据失真
- 后台统计入口被普通扫描、弱口令尝试或高频请求探测

因为：

- `/api/visit` 公开可调用，且每次请求都会增加访问计数
- `/api/event` 公开可调用，虽然已有 visitorId 去重，但仍然缺少更基础的流量限制
- `/api/stats` 已有 token 校验，但后台路径本身仍是可发现的

### 1.2 设计目标

安全加固做成“两层保护 + 两个限流点”。

#### 两层保护

第一层：平台侧保护

- 对 `/admin.html` 和 `/api/stats` 增加平台侧访问控制
- 目标是让普通用户、公开扫描器、无关流量尽量在到达页面逻辑前被挡掉
- 这层保护是“外层门禁”

第二层：应用侧保护

- 保留当前 `Bearer token` 访问方式
- 保留 `timingSafeEqual` 这种安全比较逻辑
- 这层保护是“内层口令”

这种组合的好处是：即使外层规则偶尔放过流量，应用内仍有第二层校验；即使未来平台规则调整，页面也不是裸开的。

#### 两个限流点

- `/api/visit`
- `/api/event`

### 1.3 rate limit 设计

#### `/api/visit`

建议做基础 IP 级限流：

- 单 IP 在短时间内的重复计数不应无限累加
- 对真实用户尽量无感，对刷量脚本明显增加成本

建议口径：

- 以 IP 为主键
- 采用短窗口计数或短时间去重
- 优先保护统计真实性，而不是追求绝对精确的“每次页面打开都记一次”

设计原则：

- 宁可轻微低估访问量，也不要轻易高估访问量

#### `/api/event`

建议做双重约束：

- IP 级限流
- 事件级限流或事件分桶

现有 `visitorId + once` 去重逻辑保留，但不再单独承担主要防刷职责。

推荐目标：

- `calculation_completed`、`feedback_clicked`、`return_visit` 继续保留“同一 visitor 短期只记一次”的逻辑
- `result_card_generated`、`result_shared` 允许重复，但要受 IP 节流

### 1.4 后台保护的用户体验

后台保护不应打扰普通用户，也不应让你自己运维过重。

所以这次采用“介于两者之间”的方案：

- 平台侧加一层简单保护
- 页面内 token 校验继续保留

结果上表现为：

- 普通用户几乎不会接触到后台
- 你仍然保留当前这套轻量 admin 使用方式
- 不需要为这次需求引入完整登录系统

## 二、微信社交分享预览

### 2.1 现实约束

当前项目更适合做“强化站点级预览 + 轻量结果感增强”，不适合在这一轮直接做“每个参数化链接都生成动态微信结果卡片”。

原因是：

- 现有项目结构以静态页面 + edge API 为主
- 当前分享链路本质上是参数化 URL
- 动态 OG 图会显著增加复杂度、部署要求和测试面

因此，本次目标不是“动态结果卡片”，而是让：

- 站点链接看起来更像一个完整产品
- 用户主动分享时，文本和图片更像一次真实测算结果

### 2.2 设计分层

#### 第一层：站点级预览增强

补齐并优化以下 metadata：

- `og:title`
- `og:description`
- `og:image`
- `og:type`
- `twitter:card`
- `twitter:title`
- `twitter:description`
- `twitter:image`
- `canonical`

目标：

- 在微信、QQ、社群、外链等场景分享 `cost.ahopig.com` 时，链接预览更完整、更可信、更像一个成熟工具

文案方向：

- 标题突出“算清养车成本”
- 描述突出“每周/每年成本 + 参数可调 + 本地计算”
- 封面图风格与当前页面一致，避免像广告图或营销图

#### 第二层：结果分享的轻量结果感

保留现有参数化分享 URL 机制，但优化用户主动分享时带出的内容：

- 文字分享更明确地带上核心结果
- 图片分享继续作为更强表达方式
- 分享文案中可包含：
  - 当前车型类型
  - 每周预估花费
  - 年总成本
  - 一句简短结论

这里的重点不是“做动态预览”，而是让用户发出去的文字和图片更像结果，而不是普通工具链接。

### 2.3 视觉要求

社交分享预览增强应主要发生在：

- meta 信息
- 结果图内容
- 分享文案

而不是往页面首屏再增加一堆显眼的分享 UI。

## 三、打车费用对比

### 3.1 产品目标

打车对比不是要做成第二套分析系统，而是帮助用户回答一个更接近决策的问题：

“在我当前的年里程和使用习惯下，养车和打车，哪个更划算？”

所以它应该：

- 有醒目的判断结果
- 有足够但不过量的可调参数
- 与主结果区风格统一
- 不抢走“车辆成本结果”本身的主角地位

### 3.2 呈现方式

采用“双层但轻量”的结构。

#### 第一层：轻量结论卡

在结果区新增一张打车对比结论卡。

结论卡内容建议包含 3 个核心信息：

1. 当前条件下，养车 / 打车谁更省
2. 年差额
3. 临界年里程

推荐表达口径：

- `按当前参数，打车每年约 ¥X`
- `比养车多 / 少 ¥Y`
- `当年里程低于约 Z km 时，打车更划算`

视觉要求：

- 明显，但不压过主结果卡
- 颜色更克制，不做强饱和大面积背景
- 更接近“辅助决策结论”，而不是“第二主结果”

#### 第二层：轻量参数组

在参数区新增一个折叠组，名字建议为：

- `打车对比（可选）`

参数控制在 4 项：

- 起步价
- 起步里程
- 每公里价格
- 平均单次里程

默认值采用中性口径，不绑定具体城市，并允许用户按本地价格调整。

### 3.3 信息结构

#### 桌面端

推荐结构：

- 左侧参数区：新增一个打车对比分组
- 中间分析区：
  - 顶部仍是主结果卡
  - 其下加入打车对比结论卡
  - 图表继续保留在更下方

这样做的原因：

- 结论卡能自然承接主结果
- 不会把右侧明细区挤得更乱
- 比放到页尾更有决策价值

#### 移动端

推荐顺序：

- 主结果卡
- 打车对比结论卡
- 图表
- 明细

这样移动端用户能在最短阅读路径里看到：

- 车成本是多少
- 和打车相比值不值

### 3.4 计算口径

采用现有测试里已经体现的基础模型：

- 平均单次打车成本
- 打车每公里成本
- 年打车成本
- 与养车年成本差额
- 临界年里程

优先复用当前项目中已有的打车计算逻辑与测试口径，避免设计和代码实现发生偏移。

### 3.5 视觉原则

打车对比要“有价值，但不喧宾夺主”。

具体要求：

- 不新增第二张大图表
- 不新增第二列大面板
- 不做成高存在感营销模块
- 不破坏当前桌面三栏和移动单列的节奏

它应该让用户感觉：

- “这是一个很自然的补充判断”

而不是：

- “页面又多了一套复杂功能”

## 四、文件与实现边界

预计会影响以下区域：

- `index.html`
  - 首页 metadata
  - 分享文案
  - 结果图内容
  - 参数区新增打车对比参数
  - 结果区新增打车对比结论卡
- `api/visit.js`
  - 访问接口限流
- `api/event.js`
  - 事件接口限流
- `api/stats.js`
  - 保留并适配双层保护
- `admin.html`
  - 如有需要，补更明确的后台受保护提示
- 测试文件
  - rate limit / 后台保护相关测试
  - 分享预览/文案相关测试
  - 打车对比 UI 或口径相关测试

## 五、验收标准

完成后应满足：

1. `/api/visit` 与 `/api/event` 比当前更难被随意刷高。
2. 后台入口不仅有 token 校验，还有额外一层访问保护。
3. 站点链接在微信等分享场景中，标题、描述、封面图明显比现在更完整。
4. 文字分享与图片分享能更像一次具体测算结果。
5. 页面新增一张轻量打车对比结论卡，能清楚回答“养车 vs 打车谁更省”。
6. 页面新增一组轻量打车参数，并允许用户按本地情况调整。
7. 新增模块不破坏当前整体版式平衡，主结果卡仍然是页面第一视觉重点。
8. 相关测试能覆盖新的安全、分享和打车对比行为。
